# Design System Rules

OpsLens has its own visual language. It is built for operations leaders doing focused, often stressful decision-making — not for a marketing site. The interface must feel calm, precise, and trustworthy, because the entire product is asking someone to act on an AI's read of their business without re-deriving it themselves. Every visual choice either earns that trust or spends it.

> **Source of truth:** every CSS custom property referenced below is already defined in `tokens/tokens.css` (colors, spacing, radius, and typography are in place as semantic aliases over the raw per-mode/per-breakpoint tokens generated by `tokens/build-tokens.js`; logo assets are currently staged in `/Logos` until `public/logo/` is scaffolded — see `AGENTS.md`'s Project Structure). This document describes what those tokens mean and the rules for using them; it is not asking you to invent new values. If a token named below doesn't yet exist in `tokens/tokens.css`, or its value looks different from what's documented here, treat the CSS file as correct and flag the discrepancy to the developer rather than silently reconciling it either direction.
>
> **Typography tokens are a fixed scale, not an alias of the raw breakpoint tokens.** `--font-display` through `--font-caption` are each a single `font` shorthand variable (`font-weight font-size/line-height font-family`, e.g. `--font-h1: 700 28px/36px var(--font-family-base);`) — use them as `font: var(--font-h1);`, not split into `-size`/`-line-height`/`-weight`. They're hardcoded to the exact values in the table below rather than pointed at a raw `--font-desktop-*`/`-tablet-*`/`-mobile-*` token, because none of the 8 rows maps cleanly onto a single breakpoint's named style in the token export (e.g. this table's `--font-h1` spec coincidentally matches the export's "heading 2" bold values, not "heading 1"; `--font-caption`'s 11px size doesn't exist in the export at all) — aliasing to the nearest coincidental match would have silently misnamed that token. See `tokens/build-tokens.js`'s `SEMANTIC_TYPE_SCALE` comment for the full breakdown.

## Design Principles

**Signal over noise.** Reduce unnecessary alerts, metrics, and visual complexity. Show what matters, not everything available.

**Trust is a visual property, not just a data property.** Confidence and severity must be distinguishable at a glance, not only in a tooltip — color, iconography, and typographic weight all carry meaning consistently.

**Status is never color alone.** Every severity, confidence, or lifecycle indicator pairs color with a text label and, for severity, an icon. A colorblind user or a screen reader must never lose information a sighted user gets from hue alone.

**Progressive disclosure over density.** Default views show what matters first; deeper investigation (evidence, root cause, full history) is one interaction away, not all present at once — except on the highest-density surfaces (Issues Feed, Timeline) where density is the point, see Layout, below.

**Dark mode is the primary, MVP-required surface. Light mode is a Should-Have, not a Must-Have** — see Color System, below, for why this isn't just a stylistic preference.

## Color System

### Brand

```css
--color-brand-accent: #5B8CFF;          /* focus rings, links, icons, borders, AI-related affordances — never a filled background behind white text */
--color-brand-solid: #3D63D9;           /* filled button backgrounds — the only Brand-colored surface that carries white text (Accent fails white-text contrast at 3.16:1; Solid passes at 5.27:1) */
--color-brand-solid-hover: #274EC6;     /* pointer hover on a filled Brand button (7.02:1 with white text) */
--color-brand-solid-pressed: #2040A4;   /* active/pressed state — darkest, most committed step (9.01:1 with white text) */
--color-brand-tint-subtle: rgba(91, 140, 255, 0.05);   /* barely-there AI-content highlighting */
--color-brand-tint-medium: rgba(91, 140, 255, 0.10);   /* callout boxes, AI Summary panel backgrounds */
--color-brand-tint-selected: rgba(91, 140, 255, 0.15); /* selected row/item fill (Dark mode; 0.10 in Light mode) */
```

`--color-brand-accent` and `--color-brand-solid` are not interchangeable. Accent is never used as a filled background behind white text; Solid is never used for focus rings, links, or icons. If you're building a filled button, it's Solid. If you're building anything else Brand-colored, it's Accent.

### Semantic / status

Used exclusively for severity, confidence, and health-trend indicators. Never reused for anything that isn't communicating status — see Categorical, below, for why that distinction matters.

```css
/* Dark mode (default, MVP-required) */
--color-critical: #E2726B;   /* ~5.9:1 with black fill text — see Accessibility, below, for why this isn't the raw hue's original value */
--color-high: #E08A2E;
--color-medium: #E0C22E;   /* used sparingly, always paired with a text label */
--color-success: #3FAE6B;
--color-neutral: #8890A6;  /* also the base for the Confidence "Insufficient evidence" tier */
```

Three of these five values fail WCAG AA on a white background (Medium drops as low as 1.76:1). This is why Light mode is a separate, independently-verified palette rather than the same values on a lighter surface:

```css
/* [data-theme='light'] override — Light mode, Should-Have */
--color-critical: #B23B33;   /* ~5.9:1 with black fill text */
--color-high: #A96319;       /* 4.68:1 on white */
--color-medium: #897614;     /* 4.50:1 on white */
--color-success: #308552;    /* 4.56:1 on white */
--color-neutral: #6B7590;    /* 4.59:1 on white */
```

`--color-brand-solid` and its hover/pressed steps are identical in both modes — the button's own fill is what the white text sits on, not the page behind it, so there's nothing to override.

### Categorical

For the Operational Health Score's five components and any future multi-series chart or department color-coding. Deliberately outside the red/amber/yellow/green semantic family so a category label can never be misread as a status claim — a chart segment colored "Critical red" would otherwise imply a problem when it's just identifying which component it is.

```css
--color-cat-delivery: #2DD4BF;    /* #0F766E in Light mode */
--color-cat-inventory: #A78BFA;   /* #6D28D9 in Light mode */
--color-cat-customer: #F472B6;    /* #BE185D in Light mode */
--color-cat-financial: #818CF8;   /* #4338CA in Light mode */
--color-cat-incident: #38BDF8;    /* #0369A1 in Light mode */
```

**Only the Health Score component's own colored identity uses these tokens — its score value (whether that component is doing well or poorly) uses the Semantic palette.** Never tint a category red or green to show it's struggling; the number and its trend arrow carry that meaning instead.

**Proposed dimension list, not yet confirmed with the developer:** the Data Quality Score's five dimensions (completeness, validity, consistency, uniqueness, freshness) — no schema field breaks `qualityScore` down into these yet (see `.agents/skills/db-migration-runner/SKILL.md`'s `DataImport` model), so confirm this list before building a UI around it. Whatever the confirmed set turns out to be, it must **not** reuse this palette — it's a different five-item list from the Health Score's components, and reusing these hues would falsely visually pair, say, "Delivery" with "Completeness" just because they share a swatch. Data Quality dimension names render in `--color-text-secondary`, plain; only the score value uses Semantic.

### Confidence

Ordinal (more/less certain), never reuses Semantic or Categorical hues — a Low-confidence tag rendering in Semantic red would misread as "something is wrong" rather than "the system isn't sure." Brand-tinted instead, fading as certainty decreases, reinforcing that confidence is an AI-trust signal:

```css
--color-confidence-high: #5B8CFF;          /* = --color-brand-accent; #3D63D9 in Light mode */
--color-confidence-medium: #7C93D6;        /* #5A6FA8 in Light mode */
--color-confidence-low: #8B95B0;           /* #6B7280 in Light mode */
--color-confidence-insufficient: #8890A6;  /* = --color-neutral in both modes — "insufficient evidence" is an absence-of-signal state, not a low point on the confidence ramp, so it deliberately reuses Neutral rather than inventing a fifth tint */
```

### Surfaces, text, and structure

```css
/* Dark mode */
--color-surface-base: #1A1D29;
--color-surface-elevated: #232838;   /* cards, modals, dropdowns — one step above base */
--color-text-primary: #F5F6FA;       /* headlines, highest-emphasis text */
--color-text-secondary: #B4B9CC;     /* supporting body text, labels */
--color-text-tertiary: #818798;      /* timestamps, de-emphasized metadata */
--color-border-subtle: #2A2F42;      /* decorative dividers — no contrast requirement */
--color-border-strong: #3D4359;      /* input outlines, hover/active boundaries — carries meaning, checked at 3:1 */
--color-focus-ring: #5B8CFF;         /* = --color-brand-accent */
--color-overlay: rgba(10, 12, 20, 0.6);
--color-disabled: rgba(180, 185, 204, 0.4);
```

```css
/* [data-theme='light'] override */
--color-surface-base: #F7F8FB;       /* matches tokens/tokens.css — confirmed with the developer; not pure white, which is what gives --color-surface-elevated room to read as a distinct, lighter step above it */
--color-surface-elevated: #FFFFFF;   /* + 1px border for definition at small sizes, though it's no longer relying on the border alone the way flat white-on-white would */
--color-text-primary: #1A1D29;
--color-text-secondary: #4B5165;
--color-text-tertiary: #6B7280;
--color-border-subtle: #DDE1EC;
--color-border-strong: #C4C9D9;
--color-overlay: rgba(10, 12, 20, 0.4);
--color-disabled: rgba(75, 81, 101, 0.4);
```

Naming note: `--color-text-primary` is the *highest*-emphasis text role (headlines), and body copy is `--color-text-secondary` — match this exactly rather than renaming for what reads more intuitive.

### Color semantics — what maps to what

Several enums drive badge and indicator color in this app. They're split out below by type rather than flattened into one list, so a missing value is visible by inspection instead of something you'd only catch by cross-checking the schema. Where the underlying product rules didn't pin down an exact color, that's marked explicitly rather than presented as settled — confirm with the developer before treating it as final.

**`ConfidenceLevel`** — drives `ConfidenceTag`:

| Value | Token |
|---|---|
| High | `--color-confidence-high` |
| Medium | `--color-confidence-medium` |
| Low | `--color-confidence-low` |
| InsufficientEvidence | `--color-confidence-insufficient` |

**`IssueSeverity`** — drives `SeverityBadge` in the Issue context:

| Value | Token |
|---|---|
| Critical | `--color-critical` |
| High | `--color-high` |
| Medium | `--color-medium` |
| Low | `--color-neutral` |

**`NotificationSeverity`** — also drives `SeverityBadge`, in the Notification/Event context. A distinct enum from `IssueSeverity` (`Informational` here, not `Low`) — see `code-style.md`. Pass the enum's actual value straight through; don't translate it to the other enum's spelling to reuse a code path:

| Value | Token |
|---|---|
| Critical | `--color-critical` |
| High | `--color-high` |
| Medium | `--color-medium` |
| Informational | `--color-neutral` |

**`IssueStatus`** (lifecycle) — drives the status stepper / an issue's status badge. **Proposed mapping, not yet confirmed with the developer:**

| Value | Token |
|---|---|
| Detected | `--color-neutral` |
| Reviewed | `--color-neutral` |
| Acknowledged | `--color-brand-accent` |
| InProgress | `--color-brand-accent` |
| Resolved | `--color-success` |
| Dismissed | `--color-neutral` (+ strikethrough) |

**`RecommendationStatus`** — drives a recommendation's status indicator. **Also a proposed mapping, not yet confirmed:**

| Value | Token |
|---|---|
| Pending | `--color-neutral` |
| Accepted | `--color-success` |
| Modified | `--color-brand-accent` |
| Rejected | `--color-neutral` (+ strikethrough) |
| Dismissed | `--color-neutral` (+ strikethrough) |
| Completed | `--color-success` |

Severity, confidence, and status are independent concepts and must never share a color family beyond what's explicitly listed above — a Critical issue and a Dismissed recommendation should never look alike by accident.

**A resolved or dismissed `Issue` is visually deprioritized, not just re-labeled.** Move it out of the primary Issues Feed (or visibly mute/collapse it) rather than leaving it in place with only its badge color changed.

## Typography

`--font-family-base` is Inter, with the system sans-serif stack as fallback — chosen for dense-UI legibility and a true tabular-figure variant, which matters for a product whose signature screen is numbers a user re-checks every morning.

| Token | Size / Line-Height | Weight | Usage |
|---|---|---|---|
| `--font-display` | 40px / 48px | 700 (Bold) | The Operational Health Score number — the one place in the product that earns a display-sized number. |
| `--font-h1` | 28px / 36px | 700 (Bold) | Top-of-page titles ("Morning Brief," "Issues," department names). |
| `--font-h2` | 20px / 28px | 600 (Semibold) | Section headers within a page (e.g., "AI Summary," "Suggested Actions" within Issue Detail). |
| `--font-h3` | 16px / 24px | 600 (Semibold) | Card titles, issue titles in the Issues Feed, causal-chain node labels. |
| `--font-body` | 14px / 20px | 400 (Regular) | Default UI text — descriptions, AI Summary body copy, evidence text. |
| `--font-body-emphasis` | 14px / 20px | 600 (Semibold) | Inline emphasis within body text — never a substitute for a heading level. |
| `--font-label` | 12px / 16px | 500 (Medium) | Badge and tag text (severity, confidence), table column headers, button labels. |
| `--font-caption` | 11px / 14px | 400 (Regular) | Timestamps, de-emphasized metadata — paired with `--color-text-tertiary`, which clears normal-text AA at this size (no large-text exception needed). |

**Numeric and tabular figures.** Any number that updates or is compared against another on screen — the Health Score, percentages, confidence values, dollar amounts, issue counts, deltas — uses tabular (fixed-width) figures, not proportional ones. This is a rule applied on top of whichever type token the number already uses, not a separate token: a delta in a `--font-body`-sized table cell is still `--font-body`, just with tabular figures enabled. Without this, a count changing from "9" to "12" visibly shifts surrounding layout and reads as noisier than the actual change.

**Component type mapping:**

| Component / Surface | Type Token |
|---|---|
| Operational Health Score number | `--font-display` |
| Morning Brief page title, department page titles | `--font-h1` |
| Issue Detail section headers (AI Summary, Evidence, Suggested Actions) | `--font-h2` |
| Issue title (Issues Feed row, Issue Detail header), causal-chain node label | `--font-h3` |
| AI Summary body, root-cause explanation, AI Assistant answer text | `--font-body` |
| Severity badge text, Confidence tag text | `--font-label` |
| Status stepper labels, table column headers, button labels | `--font-label` |
| Timestamps, "Last updated" text, data-source attribution | `--font-caption` |

## Spacing

Use the spacing scale already defined in `tokens/tokens.css` (`--space-*`). Do not reach for an arbitrary pixel value when a token exists — it almost always does. Apply spacing uniformly across padding, margins, and gaps rather than one-off values per component. Be generous with whitespace on the Issue Detail view especially — it's the highest-stakes, most information-dense surface in the product, so density should come from structure (Summary → Evidence → Root Cause → Recommendation), not from cramming.

## Shape, Elevation & Borders

Use the radius scale already defined in `tokens/tokens.css` (`--radius-*`); cards, buttons, and inputs stick to the small/medium steps — no per-component ad hoc radii. Borders (`--color-border-subtle` / `--color-border-strong`) are preferred over heavy shadows for separating content; shadow is reserved for true overlays (modals, dropdowns) so it retains meaning ("this is floating above the page"). Minimal, purposeful elevation — avoid stacked card-on-card effects.

## Components

Primitives live in `components/ui/`. Compose them, do not replicate them.

### Button

Filled primary uses `--color-brand-solid` with `--color-brand-solid-hover`/`--color-brand-solid-pressed` for interaction states — never `--color-brand-accent` as a filled background (see Color System, above, for why).

**One gradient token exists: `--gradient-cta`.** Approved for exactly one use — the closing call-to-action section's background on the marketing page — not a general-purpose gradient utility. Built entirely from `--color-brand-accent`/`--color-brand-solid`/`--color-brand-solid-pressed` (already-defined tokens, no new hue), generated in `tokens/build-tokens.js`'s `SEMANTIC_GRADIENTS` the same way the typography scale is hand-specified there, since gradients have no category anywhere in the Figma export. Do not reach for this on a card, a status indicator, or a second CTA without confirming with the developer first — its whole justification was "the single highest-intent action per view," and using it more than that quietly turns a deliberate accent into wallpaper.

### SeverityBadge

The only component that should ever render a severity or notification-tier indicator. Takes either an `IssueSeverity` or a `NotificationSeverity` value and looks up the correct token from the Color semantics table above — never a raw color. Always rendered with an accompanying icon, never color alone. A shared visual pattern (filled badge, icon, text) across two genuinely different enums — see `code-style.md`; the badge reflects whichever vocabulary applies to the object it's labeling and never merges them into an invented superset.

### ConfidenceTag

Renders a `ConfidenceLevel` using the Confidence token pairs above. Distinct visual treatment from `SeverityBadge` — an outlined tag with no icon, not a filled badge — so the two never visually compete when they appear on the same card (an Issue can be Critical severity and Low confidence at once; the two indicators must read as answering different questions).

### EvidencePanel

Expandable, always adjacent to the AI conclusion (Insight, root-cause explanation, or Recommendation) it supports. Never optional or hidden behind a secondary click when the conclusion itself is visible — see `.agents/skills/component-builder/SKILL.md`'s Trust-Model-Aware Components section.

### CausalChain

Root-cause visualization using directional connectors and hedged language ("likely," "contributing factor," "correlated") rather than asserting causation. Each node links back to the `Evidence` it's derived from.

### StatusStepper

Reflects an `Issue`'s lifecycle (`Detected → Reviewed → Acknowledged → InProgress → Resolved/Dismissed`) using the `IssueStatus` token mapping above.

### HealthScoreDisplay

Displays the numeric score together with its five component breakdowns — never the number alone. If a component lacks sufficient data, that component renders an explicit "insufficient data" state rather than being silently omitted or averaged around.

### Card

Rounded corners (small/medium radius), subtle border, no drop shadow by default — add shadow only when a card needs to float above a busy background.

### Input

Label sits above the input, not inside it. Error messages appear below the input using `--color-critical`, with a small icon. Focused state uses a `--color-focus-ring`-colored ring.

## Issue Detail Layout

This is the most important page in the product — the moment a user's trust in OpsLens is made or broken. Structure it exactly as: **Summary → Evidence → Root Cause → Recommendation → Human Decision Controls → Activity History.** Every section must visually distinguish confirmed data from AI-inferred content from an open human decision — never collapse that distinction for the sake of a cleaner layout.

## Morning Brief Layout

The signature daily screen. Structure: **Operational Health Score → Critical / Financial / Customer risk snapshot → single top AI recommendation → path into the Issues Feed.** At most one primary recommendation is shown by default; everything else is reachable, not displayed by default. Charts support the explanation but never dominate the initial view — decisions come before charts.

## Iconography

Proposed default: Lucide, a single consistent stroke-style icon set used end-to-end — confirm with the developer if a different library is already chosen. Whichever set is used, icons always carry an accessible label via `aria-label` or adjacent visible text; never rely on an icon alone to convey severity or status.

## Motion

In the dashboard product UI, motion is functional only — state transitions, loading indicators, expand/collapse, the streaming AI Assistant reply. No page transitions.

The public marketing page is the one documented exception: restrained decorative motion is allowed there specifically — a scroll-triggered reveal (fade + slight rise, once per element) on sections and cards, and a subtle hover lift/glow on interactive cards — to signal a modern, polished product before a visitor ever reaches the dashboard itself. Keep it quiet: no looping/ambient animation beyond a single small status-dot pulse, no motion that delays a visitor from reading or acting on content, nothing that fires more than once per element per page load.

Every case, functional or decorative, must respect `prefers-reduced-motion`.

## Accessibility

Every interactive element is reachable by keyboard, with a visible focus state using `--color-focus-ring`. Form inputs have associated labels; error messages are linked via `aria-describedby`. Images have `alt` text.

**Color contrast** — the Status tokens (`--color-critical`/`--color-high`/`--color-medium`/`--color-success`/`--color-neutral`) were originally calibrated for use as accent color against a surface, not as a badge fill with white text: white-on-fill measured as low as 1.76:1 in dark mode (Medium). `components/ui/SeverityBadge.tsx` was switched to black-on-fill, which fixed every severity except Critical. Critical's fill value was changed during the Phase 7 accessibility pass (`#D64545` → `#E2726B` in dark mode, `#D54141` → `#B23B33` in light mode) specifically to clear AA with black fill text (~5.9:1 in both modes) while staying recognizably "critical red" — a lighter, more muted red than before. `ConfidenceTag`'s text-on-surface pattern is otherwise clean (4.55–5.61) except `Insufficient evidence` in light mode against `--color-surface-base` specifically (4.32, still passes against `--color-surface-elevated` at 4.59) — every current call site renders it inside a `Card` (elevated surface), so this hasn't been hit in practice, but avoid placing it directly against the light-mode page background.

## Logo & Brand Assets

Brand assets live in `public/logo/` (scaffolded during Foundation; `/Logos` at the repo root is the original, now-superseded staging copy — see `AGENTS.md`'s Project Structure). Confirm the exact filenames and dimensions already present there rather than assuming a specific naming convention — this document doesn't fabricate ones it hasn't seen. The current `public/logo/` set (horizontal and icon lockups, each in black/blue/white, plus `opslens-horizontal-color.svg` — see below) is a richer variant scheme than the pattern below assumes — treat the pattern as a floor, not a ceiling, and don't discard variants that don't fit it. The expected pattern, matching how the rest of the design system is structured:

- A full icon+wordmark lockup and an icon-only mark, each as SVG.
- A dark-on-light and a light-on-dark variant of each, since Dark mode is this product's primary surface (the inverse emphasis of a light-only product — most usage will be the light-on-dark variant, not the dark-on-light one).
- Referenced only through a `BrandMark` component in `components/ui/`, never by importing a path from `public/logo/` directly in a feature component — if `BrandMark` doesn't exist yet, that's a sign to build it before the second place in the app needs the logo, not to duplicate an `<img>` tag.

**`opslens-horizontal-color.svg`** — added post-launch, not part of the original four-file set. `BrandMark`'s default (`tone="auto"`) dark-theme lockup is plain white; the marketing header and auth pages instead want the brand-blue icon visible in dark mode too (developer-approved via a preview comparison — see `components/ui/BrandMark.tsx`'s `Tone` type). Because the icon shape carries no legibility risk either way, only the horizontal (icon+wordmark) lockup needed a genuinely new asset: this file pairs the same `#5B8CFF` icon color the existing blue lockup already uses with a white wordmark, since that lockup's own near-black wordmark (`#12161F`) disappears against a dark surface. Opt in with `<BrandMark tone="color" />` — the default stays `"auto"` (the original all-white/all-blue scheme) so existing usages (e.g. `OrgSwitcher`'s sidebar mark) render unchanged.

## What Not to Do

- Do not add a new color without checking whether an existing token already covers the need — the palette is intentionally organized into four families (Brand, Semantic, Categorical, Confidence) precisely so it doesn't grow unchecked.
- Do not use `--color-brand-accent` as a filled background behind white text. Use `--color-brand-solid`.
- Do not reuse the Categorical palette for anything other than Health Score components/department accents — see Color System, above, for why a second unrelated five-item list (like Data Quality dimensions) must not borrow these hues.
- Do not set Low-confidence or Suggested content in a heavier font weight than confirmed/high-confidence content in the same view.
- Do not mix icon libraries.
- Do not build Issue Detail or the Morning Brief with anything less than full evidence visibility — that's the product, not a nice-to-have.
- Do not hardcode a hex value or pixel size anywhere in `components/` or `app/`. If `tokens/tokens.css` doesn't have a token for what you need, stop and ask — don't invent one inline.
